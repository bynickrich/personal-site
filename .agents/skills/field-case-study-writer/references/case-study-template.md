# Case Study Template

Use the full structure for flagship case studies. Remove empty sections rather than filling them with generic text.

## 00 — Project identification

Include only known facts:

- Project
- One-sentence description
- Role
- Organization
- Team
- Timeline
- Stack
- Scope
- Status
- Confidentiality
- Primary contribution
- Outcome or proxy outcome

## 01 — Brief

Write two or three sentences that answer:

1. What condition or problem mattered?
2. What did Nick change?
3. Why is this project relevant to a Design Engineer role?

Do not open with a journey, passion statement, or company history.

## 02 — Operating context

Explain:

- Who used the product or system
- What they were trying to accomplish
- What was breaking down
- Why the problem mattered to customers, the product, or the team

Keep business context tied to the work.

## 03 — Constraints

Include only constraints that changed the solution, such as:

- Technical architecture
- Legacy systems
- Brand requirements
- Accessibility requirements
- Confidentiality
- Team capacity
- Timeline
- Browser or device support
- Governance or ownership boundaries

Use a list when possible.

## 04 — Responsibility

State:

- What Nick owned
- What he influenced
- What he built
- What partners owned
- Where decisions were shared

This section should eliminate ambiguity, not inflate scope.

## 05 — Decision records

Use three to five records for a flagship case study.

### Decision NN — Clear decision title

**Condition**  
What fact or constraint created the decision?

**Decision**  
What did Nick or the team choose?

**Rationale**  
Why was this the right choice?

**Tradeoff**  
What did the choice cost, limit, or postpone?

**Evidence**  
What artifact, test, feedback, or result supports it?

## 06 — System specification

Show the Design Engineer layer. Include relevant proof such as:

- Component anatomy
- Component API
- Tokens
- Architecture or data flow
- State model
- Responsive rules
- Interaction behavior
- Accessibility requirements
- Content model
- Design-to-code workflow
- Documentation system

Prefer diagrams, annotated examples, and compact explanations over long prose.

## 07 — Implementation

Explain how the design became production-quality software.

Possible evidence:

- React, Next.js, TypeScript, Tailwind, or modern CSS implementation
- Loading, empty, error, and edge states
- Semantic HTML and keyboard behavior
- Responsive adaptation
- Performance decisions
- Storybook stories
- Interaction, visual, or accessibility regression tests
- Browser constraints
- Code or component examples

Do not list technology without connecting it to a product or quality decision.

## 08 — Validation

Explain how the work was checked.

Possible signals:

- Usability feedback
- Design review
- Engineering review
- Accessibility testing
- Interaction tests
- Visual regression
- Adoption
- Support feedback
- Analytics
- QA findings

State limitations directly.

## 09 — Outcome

Use measured outcomes when available. Otherwise use credible proxy outcomes such as:

- Adoption
- Reduced duplicated patterns
- Improved consistency
- Improved accessibility
- Faster prototyping
- Reduced handoff ambiguity
- Clearer governance
- Better documentation
- Positive engineer or stakeholder feedback
- Improved QA process

Do not imply causality that the evidence cannot support.

## 10 — Revision notes

Answer:

- What worked?
- What was difficult?
- What would Nick change now?
- What did he learn?
- What should be measured next?

Write from current judgment rather than pretending the original work was perfect.

## Compact project entry

For supporting work, use:

1. Brief
2. Responsibility
3. One decision or implementation proof
4. Outcome
5. Current reflection or next step
