# Portfolio Visual Direction

## Working Name

**Industrial Field System**

A clarity-first visual system for a frontend-leaning Design Engineer portfolio. The aesthetic borrows from NASA systems manuals, military specification graphics, aerospace interfaces, civic infrastructure, printed field documentation, industrial editorial design, and restrained command-center software.

The goal is not to create a themed website. The goal is to make the portfolio feel precise, operational, trustworthy, technical, and high-craft while keeping the work easy to understand.

## Core Direction

This portfolio should feel like a polished mission briefing for design engineering work.

It should communicate:

Nick Richardson is a Design Engineer with deep product-design roots. He designs thoughtful software experiences and builds polished frontend systems with React, Next.js, TypeScript, Tailwind, and modern CSS.

The visual system should support that message by making the work feel:

* Clear
* Structured
* Technical
* Premium
* Durable
* Systematic
* Human-readable
* Production-minded

The design should feel like professional infrastructure, not entertainment UI.

## Aesthetic Summary

The visual language combines:

* NASA systems manual discipline
* Military specification typography and metadata
* Aerospace and F-22-style material restraint
* IBM-era computing seriousness
* Civic infrastructure clarity
* Industrial editorial confidence
* Command-center information density
* Grainy printed documentation texture
* Modern product software usability

The result should feel like a field manual for high-quality interface work.

## Strategic Ratio

Use this operating ratio:

**70% hiring clarity / 30% visual worldbuilding**

The portfolio must always answer the hiring questions first:

* Who is Nick?
* What role does he want?
* What kind of work does he do?
* What makes him credible?
* Where should I click next?

The aesthetic should create confidence and memorability, but it should never slow down comprehension.

* Disciplined typography
* Controlled color
* Consistency over decoration

Do not borrow:

* Fake mission lore

### Military Specification Graphics

Borrow:

* Stenciled confidence
* Numbering systems
* Grid logic
* Serial labels
* Technical metadata
* Restricted color usage
* Functional hierarchy

Do not borrow:

* Aggressive language
* Tactical cosplay
* Overuse of stencil type

### Civic Infrastructure

Borrow:

* Accessibility

* Utility over ornament

Do not borrow:

* Government blandness

### Industrial Editorial Design

Borrow:

* Confident typography
* Material texture
* Strong layout rhythm
* Concise copy
* Sharp section pacing
* Serious brand presence

Do not borrow:

* Empty marketing swagger
* Vague industrial buzzwords
* Style without proof

## Typography

Use the IBM Plex family as the initial type system.

### Display

**IBM Plex Sans Condensed**

Use for:

* Hero headings
* Section titles
* Project titles
* Large editorial labels
* Case study mastheads
* Big numeric identifiers

Guidance:

* Use large.
* Use confidently.
* Use sparingly.
* Keep line-height tight.
* Avoid making every heading enormous.

The display type should feel like aerospace signage and field documentation, not a sports poster.

### Body / UI

**IBM Plex Sans**

Use for:

* Body copy
* Project summaries
* Navigation
* Buttons
* Captions
* Case study writing
* Interface text

Guidance:

* Prioritize readability.
* Use generous line-height for case study content.
* Keep body text calm and trustworthy.
* Let the work be easy to read.

### Mono

**IBM Plex Mono**

Use for:

* Metadata
* Labels
* Stack tags
* Project IDs
* Status indicators
* Code snippets
* Timestamps
* Short operational notes

Guidance:

* Use as seasoning, not as the main voice.
* Avoid making the whole site feel like a fake terminal.
* Mono should create system texture and technical clarity.

## Type Personality

The type system should feel:

* Dense but readable
* Technical but human
* Editorial but not precious
* Industrial but not brutal
* Serious but not cold

A simple pattern:

* Body copy = trustworthy software
* Mono labels = operational metadata
* Condensed display = industrial authority

## Color System

The palette should be built from:

* Warm paper
* Carbon ink
* Gunmetal
* Steel gray
* Institutional blue
* Safety orange
* Restricted red
* Functional status colors

Recommended usage ratio:

**90% paper / ink / steel**
**8% institutional blue**
**2% signal orange or red**

### Light Theme

The light theme should feel like a technical field manual:

* Warm off-white background
* Carbon-black foreground
* Muted steel borders
* Pale industrial panels
* Blue as the main accent
* Orange only for rare signal moments

### Dark Theme

The dark theme should feel like blackened gunmetal:

* Very dark blue-gray background
* Aged white foreground
* Muted steel panels
* Blue as a readable accent
* Orange as a rare signal color
* No neon glow by default

### Color Discipline

Do not use color as decoration.

Use color to signal:

* Priority
* Interaction
* Status
* Navigation
* Callouts
* System identity

Avoid:

* Rainbow tag systems
* Neon gradients
* Overuse of red/orange
* HUD-style glowing outlines
* Color combinations that reduce readability

## Texture

Texture should add material quality without hurting readability.

Use:

* Subtle fixed grain overlay
* Light paper noise
* Very subtle grid fields
* Thin border rules
* Occasional inset surface treatment

Avoid:

* Heavy scanlines
* Animated glitches
* CRT effects
* Dirty grunge textures
* Noise that makes text harder to read

Texture should feel like printed documentation or anodized industrial material, not a filter.

## Layout

The layout should be built on:

* Strong grids
* Strict alignment
* Modular cards
* Clear vertical rhythm
* 12-column desktop structure
* Readable text measures
* Consistent section spacing
* Reusable metadata modules

Use dense information only when it is organized clearly.

Avoid:

* Chaotic masonry grids
* Hidden navigation
* Splash screens
* Overlapping elements that reduce readability
* Layout tricks that slow the reviewer down

The user should always know where they are, what they are looking at, and what to do next.

## Surfaces

Use a small set of reusable surface types:

### Surface Base

The page-level background.

Use for:

* Overall site shell
* Case study pages
* Main content backgrounds

### Surface Panel

The cleanest primary content container.

Use for:

* Hero modules
* Case study summary panels
* Main content cards
* Important sections

### Surface Plate

The more industrial/heavy card.

Use for:

* Project cards
* Metadata blocks
* Artifact previews
* Technical notes
* Supporting modules

### Surface Muted

A quieter secondary surface.

Use for:

* Notes
* Context blocks
* Secondary explanations
* Code-adjacent panels

Surface treatments should feel physical and precise, but never bulky.

## Shape Language

The shape system should be mostly rectangular and disciplined.

Use:

* Thin borders
* Small radii
* Corner cuts
* Bracket corners
* Inset rules
* Strong edges

Avoid:

* Large bubbly rounded corners
* Heavy shadows
* Excessive glassmorphism
* Overdecorated HUD frames
* Random notches on every card

Corner treatments should be rare enough to feel intentional.

## Grid and Field Elements

Grid fields are atmosphere, not content.

Use them for:

* Hero backgrounds
* Section transitions
* Empty states
* Technical artifact areas
* Visual rhythm behind simple layouts

Avoid using grid fields behind long-form text unless contrast remains excellent.

The grid should support the feeling of measurement, structure, and technical precision.

## Motion

Motion should be small, physical, and useful.

Use:

* Subtle hover refinement
* Focus feedback
* Short reveal motion
* Small transitions
* Demo loops when explaining interaction
* Reduced-motion support

Avoid:

* Large page transitions
* Fake glitches
* Constant animated chrome
* Scanline animation
* Motion that competes with reading
* Motion that makes the portfolio feel like a game UI

Motion should clarify state, not show off.

## Interaction Style

Interactions should feel precise and keyboard-friendly.

Use:

* Clear focus states
* Direct CTAs
* Command-palette influence where useful
* Copy-link affordances
* Filterable project indexes only if needed
* Artifact drawers only if they help comprehension

Avoid:

* Hidden controls
* Mystery navigation
* Terminal-only flows
* Overly clever hover states
* Requiring exploration to understand the site

The best interaction pattern is the one that helps someone review the work faster.

## Tailwind / Implementation Notes

The visual system is built around semantic utilities and theme-scoped CSS variables.

Core idea:

Tailwind utilities are the API. Theme scopes change the values behind that API.

Examples:

* `bg-background`
* `text-foreground`
* `bg-panel`
* `text-muted-foreground`
* `border-border`
* `button-primary`
* `surface-panel`
* `type-hero`
* `system-badge`

Theme scopes:

* `theme-industrial-light`
* `theme-industrial-dark`

Use theme classes high in the tree, ideally on the root layout, body, or a major wrapper.

Avoid theme-hopping across the main portfolio. Local theme scopes are acceptable for Labs or isolated demos, but the main portfolio should feel cohesive.

## Accessibility and Quality Rules

This visual direction only works if the fundamentals are strong.

Required:

* High color contrast
* Visible focus states
* Keyboard navigation
* Good semantic HTML
* Reduced-motion support
* Responsive layouts
* Readable body copy
* Clear heading hierarchy
* No broken links
* Fast page loads

The site should prove production quality through execution, not through claims.

## Review Questions

Before shipping any page or component, ask:

1. Does this make the portfolio easier to understand?
2. Does this help someone see Nick as a Design Engineer?
3. Does this support product judgment, systems thinking, or frontend craft?
4. Is the aesthetic helping the work, or competing with it?
5. Would a recruiter know where to click?
6. Would a design leader trust the taste level?
7. Would a frontend engineer see production-minded decisions?
8. Does this still work without motion?
9. Is the copy specific and credible?
10. Is this premium, or is it costume design?

## Final Principle

The portfolio should feel like a high-end technical briefing for real software work.

The aesthetic is there to create confidence, structure, and memorability. The work still has to lead.

When in doubt, choose clarity over lore, evidence over atmosphere, and restraint over spectacle.
